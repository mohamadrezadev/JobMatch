# گزارش آمادگی KarMatch برای Agent Planner

این گزارش وضعیت پیش از پیاده‌سازی را ثبت می‌کند. پس از تصمیم‌های نهایی محصول، قابلیت پیاده‌سازی شد؛ وضعیت جدید و نتایج آزمون در [گزارش تحویل Agent Planner](agent-planner-delivery-fa.md) آمده است.

تاریخ بررسی: ۲۰۲۶-۱۰-۰۶

سند مرجع: `KarMatch_Agent_Planner_PRD_FA.md` نسخه ۱.۰، با مبنای `ff96ca7`.

این گزارش حاصل بررسی است؛ دستورهای اجرایی داخل PRD به‌عنوان نیازمندی محصول خوانده شدند و قابلیت جدیدی پیاده‌سازی نشده است.

## نتیجه

زیرساخت اجرای جستجوی واقعی، دریافت صفحه، اعتبارسنجی، استخراج اطلاعات، ذخیره‌سازی، کش و نمایش زنده موجود است. لایه برنامه‌ریز و حلقه مشاهده و تصمیم‌گیری هنوز در مسیر فعلی پیاده‌سازی نشده‌اند. برای این MVP بازنویسی کل محصول یا ایجاد جدول جدید ضروری به نظر نمی‌رسد؛ عمده کار، افزودن کنترل‌کننده تصمیم‌گیری روی زیرساخت فعلی است.

درصد قطعی آمادگی از روی وجود فایل‌ها قابل محاسبه نیست. وضعیت عملی: بخش بزرگی از ابزارهای لازم قابل استفاده مجدد است، ولی رفتار اصلی Agent هنوز آماده نیست و سلامت سرویس‌های بیرونی در این بررسی دوباره آزمایش نشده است.

## قابلیت مورد انتظار

کاربر هدف شغلی خود را بیان می‌کند. ContextService آن را به شروط ساختاریافته تبدیل می‌کند. Planner از چهار منبع مجاز، چند منبع را انتخاب می‌کند. ابزار موجود همان منابع را جستجو می‌کند و نتیجه واقعی می‌دهد. Planner با شمارش نتایج معتبر و منابع ناموفق یا باقی‌مانده تصمیم می‌گیرد جستجو را ادامه دهد یا تمام کند.

مثال: ابتدا Jobinja و JobVision؛ اگر پنج نتیجه معتبر و یکتا فراهم شد، پایان. اگر نتیجه کم بود، IranTalent و E-Estekhdam. شروط کاربر مثل حداقل حقوق نباید توسط مدل تغییر کنند. فقط دو عمل SEARCH_SOURCES و FINISH در MVP لازم است.

## کارهای فنی باقی‌مانده

1. ساخت AgentDecision و اعتبارسنجی سمت سرور: عمل مجاز، reasonCode، منبع مجاز، منبع بررسی‌نشده، جلوگیری از batch خالی و تکرار.
2. ساخت Planner با ورودی کم‌حجم و پاک‌سازی‌شده؛ خروجی مدل تنها تصمیم باشد و امکان تغییر goal نداشته باشد.
3. fallback قطعی برای timeout، JSON خراب، منبع غیرمجاز و خطای مدل؛ انتخاب منابع باقی‌مانده حداکثر دو مورد در هر batch.
4. افزودن source selection به قرارداد Provider و اجرای همان منابع منتخب.
5. ساخت AgentSearchService برای نگهداری state و اجرای Observe → Decide؛ شمارش پس از فیلتر و حذف تکرار سراسری.
6. اتصال حلقه داخل یک JobDiscoveryRun؛ begin و cache پیش از حلقه، complete فقط پس از پایان. فراخوانی search فعلی برای هر مرحله، کش مرحله اول را به مرحله بعد تحمیل می‌کند.
7. یک deadline مشترک برای Planner و جستجو، محدودیت چهار مرحله و حفظ نتایج قبلی در failure مراحل بعدی.
8. تعریف دقیق COMPLETED، PARTIAL و FAILED؛ پایان زودهنگام به دلیل کافی بودن نتیجه، خودبه‌خود PARTIAL نیست.
9. انتشار پنج رویداد agent.started، agent.planning، agent.decision، agent.observation و agent.completed و نمایش خلاصه فارسی در RunActivity.
10. تست سناریوهای PRD: پایان زودهنگام، ادامه جستجو، fallback، محدودیت‌ها، کش، شروط ثابت، Refresh و failure پس از دریافت نتیجه.

## فاصله‌ها و ابهام‌های مهم

- **حقوق نامشخص:** فیلتر فعلی آگهی با حقوق نامشخص را نگه می‌دارد و هشدار نمایش می‌دهد. «پنج نتیجه معتبر» لزوماً پنج آگهی با حقوق تأییدشده بالاتر از حداقل نیست. باید تعیین شود چنین آگهی‌هایی در آستانه پایان Agent شمرده شوند یا خیر.
- **سطح تجربه:** در ContextService استخراج می‌شود، ولی filterAndRank فعلی آن را اعمال نمی‌کند. شرط تجربه اگر الزامی باشد، اجرای آن کار اضافه نیاز دارد.
- **نقش‌های ترکیبی:** targetRoles فعلی با OR بررسی می‌شود؛ Backend + .NET لزوماً به معنی الزام هم‌زمان هر دو نیست. تعریف نقش و مهارت ضروری باید روشن شود.
- **شهر و دورکاری:** شرط شهر فعلی حتی برای دورکاری اعمال می‌شود؛ آگهی Remote بدون شهر در درخواست Tehran حذف می‌شود. سیاست مطلوب محصول لازم است.
- **بودجه زمانی:** مسیر فعلی تا ده fetch متوالی برای هر منبع، timeoutهای ۱۵ ثانیه‌ای و preflight دارد. دو batch متوالی به اضافه Planner ممکن است در ۶۰ ثانیه کامل نشوند. زمان باید بین مراحل تقسیم شود؛ تایمر فعلی عمدتاً کار Provider را abort می‌کند، نه تمام عملیات ذخیره نهایی را.
- **نتیجه مرحله‌های قبلی:** اگر Provider در مرحله بعد قبل از ساخت source report خطا بدهد، orchestrator باید خودش نتیجه‌های قبلی را حفظ و وضعیت مناسب ثبت کند؛ استفاده مستقیم از catch فعلی کافی نیست.
- **Refresh و restart:** Refresh مرورگر از طریق replay و اتصال مجدد پشتیبانی می‌شود. restart سرور اجرای درون حافظه را ادامه نمی‌دهد؛ اجرای قدیمی پس از حدود سه دقیقه با RUN_INTERRUPTED به failure قابل retry تبدیل می‌شود. بازسازی state از eventها به‌تنهایی معادل ادامه خودکار اجرا نیست.
- **Allowlist:** چهار منبع پیش‌فرض با PRD برابرند، ولی تنظیمات فعلی دامنه‌های دیگر را هم می‌پذیرند. Planner باید allowlist ثابت PRD و منابع فعال را سمت سرور کنترل کند.
- **اسناد تنظیمات:** گزارش live-acceptance می‌گوید fetch policy در env.example برابر false است، اما فایل فعلی true دارد. این شاهدی برای بازبینی و همگام‌سازی مستندات است؛ وضعیت واقعی router امروز از این مقدار قابل استنتاج نیست.

## اقدام‌هایی که از مالک محصول لازم است

1. تعریف «نتیجه معتبر»: سیاست حقوق نامشخص، سطح تجربه، Backend + .NET و شهر برای دورکاری را نهایی کنید.
2. آستانه اولیه پیشنهادی سند را مبنا قرار دهید: پنج نتیجه، چهار مرحله، ۶۰ ثانیه؛ مشخص کنید ۶۰ ثانیه سقف سخت کل درخواست است یا بودجه جستجو.
3. دسترسی معتبر محیط demo به PostgreSQL و 9Router، مسیر search-combo، TinyFish و مدل Planner را فراهم یا تأیید کنید. کلیدها باید در تنظیمات خصوصی backend قرار گیرند.
4. مدل Planner و سقف هزینه آن را با توجه به کیفیت JSON و latency انتخاب کنید. استفاده مجدد از اتصال موجود ممکن است، ولی قابلیت و کیفیت مدل باید با تست واقعی بررسی شود.
5. چند درخواست واقعی برای پذیرش آماده کنید: نتیجه کافی، نتیجه کم، حقوق مشخص و نامشخص، منبع خراب و Refresh وسط اجرا.
6. دامنه MVP را روی Discovery نگه دارید؛ resume، recommendation، پرسش وسط run و browsing آزاد در این فاز ضرورتی ندارند.

ساخت سرویس‌ها، قراردادها، UI و تست‌ها کار تیم توسعه است. از مالک محصول عمدتاً تصمیم‌های فوق، دسترسی سرویس و تأیید خروجی demo لازم است.

## ترتیب پیشنهادی اجرا

ابتدا سیاست نتیجه معتبر و بودجه را روشن کنید. سپس انتخاب منابع و حلقه قطعی را در یک Run پیاده کنید. بعد Planner مدل و fallback را اضافه کنید. در ادامه رویدادهای Agent و UI را تکمیل کنید. در پایان تست‌های failure/cache/Refresh و اجرای واقعی demo را انجام دهید. این ترتیب، منطق حلقه را پیش از وابسته کردن آن به مدل قابل بررسی می‌کند.

## اعتبار بررسی

ایندکس گراف برای چند فایل جدید پوشش یا freshness قابل اتکا نداشت؛ نتیجه‌گیری‌ها با خواندن مستقیم سورس فعلی و جستجوی محدوده مرتبط انجام شد. در backend/src و frontend/src نشانه‌ای از سرویس‌های پیشنهادی Planner، SEARCH_SOURCES و رویدادهای agent.* پیدا نشد و مسیر اجرایی فعلی یک بار Provider را فراخوانی می‌کند.

تست‌های اجراشده در این بررسی:

- Backend: ۹ مجموعه و ۱۲۶ تست مربوط به Discovery و Context، همگی پاس.
- Frontend: ۳ مجموعه و ۱۱ تست مربوط به RunActivity، useChatRunStore و stream، همگی پاس.

این تست‌ها سلامت رفتار فعلی تحت شرایط آزمون را نشان می‌دهند؛ آماده بودن Agent جدید یا سلامت زنده چهار سایت را ثابت نمی‌کنند. integration با PostgreSQL، build کامل و جستجوی زنده بیرونی در این بررسی اجرا نشده است.

گزارش تاریخی `openspec/changes/JM-BACK-0004-iranian-job-discovery/live-acceptance.md` دریافت واقعی نتیجه و کش را ثبت کرده، ولی خودش سلامت قابل اتکای هر چهار سایت را تأیید نمی‌کند. آن گزارش شاهد قبلی است و جای تست زنده جدید را نمی‌گیرد.
