# تحویل Agent Planner کارمچ

تاریخ: ۲۰۲۶-۱۰-۰۶

تصمیم‌های نهایی مالک محصول در حلقه Discovery پیاده‌سازی شدند. این تغییر در workspace محلی است و روی Production منتشر نشده است.

## رفتار پیاده‌سازی‌شده

عنوان شغلی محدود به Backend، .NET یا فهرستی از نقش‌های نرم‌افزاری نیست. عنوان آزاد فارسی و انگلیسی از درخواست روشن یا عنوان کوتاه کاربر استخراج می‌شود؛ aliasهای قبلی فقط برای نرمال‌سازی عنوان‌های شناخته‌شده استفاده می‌شوند. حسابدار، مدیر محصول، پرستار، کارشناس فروش، Data Engineer، UX Researcher و عنوان‌های خارج از فهرست قبلی با تست پوشش داده شده‌اند. متن مبهم یا صرفاً شرط حقوق/شهر/حضور، عنوان شغلی فرض نمی‌شود. برای عنوان‌های آزاد، همه واژه‌های عنوان باید در عنوان آگهی وجود داشته باشند؛ این نسخه ترجمه یا تطبیق معنایی بین نام‌های متفاوت یک شغل انجام نمی‌دهد.

- Planner خروجی ساختاریافته SEARCH_SOURCES یا FINISH تولید می‌کند. دامنه‌ها، تعداد منابع هر batch، reasonCode و شکل کامل تصمیم در سرور اعتبارسنجی می‌شوند. خروجی نامعتبر، خطای مدل و timeout به انتخاب قطعی منابع باقی‌مانده برمی‌گردند.
- چهار منبع مجاز عبارت‌اند از Jobinja، JobVision، IranTalent و E-Estekhdam. منابع غیرفعال در تنظیمات جستجو نمی‌شوند و منابع بررسی‌شده تکرار نمی‌شوند.
- تصمیم‌های مدل بر اساس goal ثابت و آمار مشاهده‌شده گرفته می‌شوند؛ HTML، شرح آگهی و خطای خام Provider به Planner ارسال نمی‌شوند. مدل امکان تغییر حقوق یا سایر شروط کاربر را ندارد.
- سقف جستجو چهار مرحله و حداکثر ۶۰ ثانیه است. زمان باقی‌مانده بین batchها تقسیم می‌شود. بودجه شامل Planner و ابزار جستجو است؛ ثبت و ذخیره نهایی دیتابیس پس از توقف جستجو انجام می‌شود و زمان کل پاسخ می‌تواند کمی بیشتر باشد.
- شمارش پنج نتیجه پس از فیلتر و حذف تکرار سراسری انجام می‌شود. اگر حداقل حقوق تعیین شده باشد، فقط salaryMin ماهانه به تومان و برابر یا بالاتر از حداقل، نتیجه قابل‌تأیید محسوب می‌شود. صرف salaryMax کافی نیست. حقوق نامشخص یا دوره/واحد نامشخص نمایش داده می‌شود ولی در آستانه پنج نتیجه شمرده نمی‌شود.
- اگر کاربر حداقل حقوق تعیین نکرده باشد، نبود حقوق مانع شمارش یک نتیجه مطابق دیگر شروط نیست. این برداشت در شروع پیاده‌سازی اعلام شد.
- Backend + .NET به Role=Backend و requiredSkills=.NET تبدیل می‌شود. هر دو الزام دارند. Context قدیمی با دو نقش Backend و .NET هم در فیلتر با همین معنا بررسی می‌شود.
- تجربه صریح Junior/Mid/Senior شرط سخت است؛ تجربه نامشخص آگهی هم در چنین درخواستی حذف می‌شود. اگر شرط صریح وجود نداشته باشد، سطح تجربه Profile صرفاً در رتبه‌بندی اثر دارد.
- Remote بدون شهر پذیرفته می‌شود و هشدار شهر نامشخص دارد. برای OnSite/Hybrid، در صورت درخواست شهر، شهر باید تطبیق داشته باشد. Remote با شهر معلوم همچنان با شهر درخواستی بررسی می‌شود.
- تمام مراحل داخل یک JobDiscoveryRun هستند. کش پیش از Planner بررسی می‌شود. روی cache hit هیچ تصمیم مدل یا جستجوی جدیدی انجام نمی‌شود.
- نتایج قبلی هنگام failure یا timeout batch بعدی حفظ می‌شوند؛ حتی candidateهایی که پیش از timeout به‌صورت تدریجی رسیده‌اند در نتیجه نهایی باقی می‌مانند. ذخیره تدریجی پیش از انتشار وضعیت پایانی تخلیه می‌شود.
- کافی بودن نتایج و پایان زودهنگام، در نبود خطای منبع، COMPLETED است. نتیجه قابل استفاده همراه timeout یا failure، PARTIAL است. شکست همه منابع بدون نتیجه قابل استفاده، FAILED است.
- رویدادهای agent.started، agent.planning، agent.decision، agent.observation و agent.completed ثبت و از SSE ارسال می‌شوند. UI فقط خلاصه‌های فارسی تعریف‌شده را نشان می‌دهد؛ reasoning مدل نمایش داده نمی‌شود.
- متادیتای plannerMode در تصمیم‌ها مشخص می‌کند تصمیم از model آمده یا fallback؛ این اطلاعات در UI محصول نمایش داده نمی‌شود.
- شناسه گفتگوی فعال در URL نگه داشته می‌شود تا Refresh وسط Search همان گفتگو و Run را بازگرداند. شروع گفتگوی جدید این پارامتر را پاک می‌کند. ادامه خودکار پس از restart سرور اضافه نشده و مسیر interrupted/Retry قبلی باقی است.

## فایل‌های اصلی

- `backend/src/modules/job-discovery/application/agent-planner.service.ts`: قرارداد تصمیم، فراخوانی مدل، اعتبارسنجی و fallback.
- `backend/src/modules/job-discovery/application/agent-search.service.ts`: حلقه، state، مشاهده، محدودیت‌ها و حفظ نتیجه.
- `job-discovery.service.ts`: lifecycle واحد، کش و اتصال حلقه.
- `discovery.ports.ts` و `nine-router-job-discovery.provider.ts`: دریافت منابع منتخب.
- `context.service.ts`، `conversation.ts` و `discovery.ts`: فناوری الزامی، فیلتر تجربه، موقعیت دورکار و شمارش حقوق قابل تأیید.
- `prisma-discovery.repository.ts`: دریافت تجربه Profile برای ranking.
- `job-discovery.module.ts`: اتصال Planner و Orchestrator به مسیر واقعی برنامه.
- `RunActivity.tsx` و `ChatExperience.tsx`: نمایش تصمیم و بازیابی گفتگو پس از Refresh.

جدول جدید و migration دیتابیس لازم نشد. مسیر ChatRunService، Matching و Resume بازنویسی نشده‌اند.

## تنظیم محیط

متغیر جدید `AGENT_PLANNER_MODEL` تنها مدل Planner را تعیین می‌کند. اگر خالی باشد، OPENAI_MODEL و سپس agents استفاده می‌شود. کلید و base URL از تنظیمات خصوصی backend گرفته می‌شوند.

در آزمایش واقعی، alias فعلی agents در Router مشترک به upstream نامعتبر mimo-auto رسید و HTTP 400 داد. مدل منتشرشده `ag/gemini-3-flash` در همان Router آزمایش شد و تصمیم معتبر را حدود ۱٫۶ ثانیه‌ای برگرداند. تنظیم خصوصی محلی backend/.env برای Planner روی همین شناسه قرار گرفت؛ کلید یا محتوای خصوصی env وارد Git نشد. تنظیم مدل سایر قابلیت‌ها عوض نشد.

برای Production، متغیر AGENT_PLANNER_MODEL را روی مسیر سالم و آزموده‌شده در Router همان محیط قرار دهید و backend را با تنظیم جدید اجرا کنید. سالم بودن یک alias در فهرست مدل‌ها به‌تنهایی برای پذیرش کافی نیست؛ باید پاسخ واقعی آن بررسی شود. مسیر agents مورد استفاده سایر قابلیت‌ها نیز اگر همین Router باشد نیازمند بررسی جداگانه است.

## نتیجه آزمون‌ها

- ۲۴۰ تست واحد backend پاس شدند؛ شامل عنوان‌های شغلی دلخواه و غیرنرم‌افزاری و جمله واقعی «دنبال شغل حسابداری میگردم توی تهران 5 تا اگهی برام پیدا کن».
- ۵۹ تست واحد frontend پاس شدند.
- در بررسی اولیه، ۲۲ تست integration، شامل HTTP، SSE و PostgreSQL واقعی، پاس شدند. پس از تعمیم عنوان شغلی، مجموعه HTTP چت دوباره اجرا شد و هر ۹ تست، شامل سناریوی حسابدار، پاس شدند.
- Build backend و frontend پاس شدند.
- تست مرورگر `frontend/scripts/verify-live-chat.cjs` پاس شد: تصمیم فارسی Agent، عدم نمایش reasoning، Refresh واقعی وسط جستجو، اتصال مجدد از cursor، حذف رویداد/Job تکراری، نتیجه partial، Retry، بازیابی تاریخچه و نمای موبایل. داده‌های این تست مرورگر fixture صریح هستند؛ شاهد سلامت سایت‌های واقعی نیستند.
- تست‌های جدید مدل شامل JSON نامعتبر، JSON داخل code fence، منبع نامجاز یا تکراری یا بررسی‌شده، پایان زودهنگام نامعتبر، timeout و failure هستند. تست‌های حلقه شامل کافی بودن نتیجه، حقوق uncertain، حفظ نتیجه در failure/timeout، شروط تغییرناپذیر، منابع فعال و cache هستند.

## اجرای زنده با سرویس واقعی

اسکریپت `backend/scripts/verify-agent-live.cjs` اضافه شد. با حساب آزمایشی موقت، Router و سایت‌های واقعی کار می‌کند؛ lifecycle، event sequence، منابع مجاز، فیلتر نتیجه، یک Run واحد و cache را بررسی می‌کند. حساب و گفتگوی آزمایشی پس از اجرا حذف می‌شوند؛ آگهی‌های واقعی ذخیره‌شده، داده مشترک محصول هستند و حذف نمی‌شوند.

برای اجرای آن از پوشه backend، پس از build و راه‌اندازی API محلی:

```powershell
$env:JOBMATCH_LIVE_AGENT = 'true'
node scripts/verify-agent-live.cjs
```

آدرس پیش‌فرض API برابر http://127.0.0.1:3100 است و با JOBMATCH_API_URL قابل تغییر است. پیام پیش‌فرض «کار بک‌اند دات نت تهران می‌خوام» است و با JOBMATCH_AGENT_PROMPT قابل تغییر است. اسکریپت بدون opt-in جستجوی واقعی انجام نمی‌دهد.

دو اجرای واقعی اولیه انجام شد:

| اجرا | تصمیم مدل | fallback | آگهی واقعی پذیرفته‌شده | پایان |
|---|---:|---:|---:|---|
| alias اولیه agents | ۰ | ۲ | ۲ | سقف زمان؛ PARTIAL |
| مدل مستقل Planner | ۱ | ۱ | ۱ | سقف زمان؛ PARTIAL |

در هر دو اجرا، چهار منبع به timeout رسیدند، اما نتایج دریافت‌شده حفظ و ذخیره شدند و درخواست مجدد از کش پاسخ گرفت. اجرای دوم نشان داد فراخوانی مدل واقعی و fallback هر دو در مسیر اصلی کار می‌کنند. تعداد نتیجه در این پیام ثابت بین اجراها متفاوت بود؛ تضمین پنج آگهی در ۶۰ ثانیه حاصل نشده است.

پس از گزارش جمله «دنبال شغل حسابداری میگردم توی تهران 5 تا اگهی برام پیدا کن»، خطای جدا نکردن «میگردم»، «توی» و درخواست تعداد آگهی از عنوان شغلی اصلاح شد. در API واقعی، عنوان به «حسابداری» و شهر به Tehran تبدیل شد؛ فیلتر عنوان نیز «حسابدار» و «حسابداری» را معادل می‌گیرد. اجرای زنده همین جمله با یک تصمیم مدل و یک مرحله، ۶ آگهی مطابق فیلتر ذخیره کرد و با ENOUGH_RESULTS تمام شد. گزارش هر دو منبع jobinja/jobvision همچنان TIMEOUT داشت، اما آگهی‌های دریافت‌شده پیش از پایان زمان حفظ شدند. این اجرا شاهد موفقیت همین درخواست است؛ تضمین پایداری منابع در اجراهای بعدی نیست.

## کار باقی‌مانده برای دمو

1. تنظیم مدل مستقل Planner و کلیدهای خصوصی در محیط Production، سپس اجرای smoke همان محیط.
2. رفع یا تنظیم مسیر خراب agents در Router برای قابلیت‌های دیگری که از آن استفاده می‌کنند.
3. بهبود latency و پایداری منابع یا انتخاب Promptهای واقعی که در بودجه موجود نتیجه دارند؛ نباید درخواست Backend .NET تهران را بدون آزمایش، سناریوی تضمینی «پنج نتیجه کافی» نامید.
4. تکرار سناریوهای حقوق و تجربه صریح با داده واقعی و بررسی نرخ نتیجه نامشخص؛ سناریوهای خرابی منبع و Refresh در تست‌های کنترل‌شده پوشش دارند.

قابلیت محلی پیاده‌سازی و آزموده شده است؛ محدودیت فعلی آمادگی دمو، پایداری سرویس‌های بیرونی و تنظیم صحیح محیط Production است.
